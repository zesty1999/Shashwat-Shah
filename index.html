Case Study 01

Banking & NBFC Investment Platform

Fixerra — FD, RD, Credit Card & Savings products, sold through bank and NBFC partners

Problem

Users invest in fixed deposits, recurring deposits, credit cards, and savings products from partner banks (AU Small Finance Bank, Suryoday Small Finance Bank, Unity Bank) and NBFCs (Bajaj, Mahindra, Shriram). Every partner exposes a different API shape, different failure behaviour, and different timing guarantees — and none of that can be allowed to lose or duplicate money, or leave a user's investment in an unknown state.

Architecture

A distributed backend of 10+ microservices (Node.js, NestJS, TypeScript) with MySQL/PostgreSQL as the system of record, Redis for caching, and AWS (Lambda, SQS, EventBridge, CloudWatch) handling asynchronous work. Each bank/NBFC integration lives in its own service, isolated from the core user and investment flows by async messaging — so a slow or misbehaving partner API can't take down onboarding or booking for everyone else.

  1. User
  2. API Gateway
  3. User Service
  4. Investment Service
  5. Queue (SQS)
  6. Bank / NBFC Integration Service
  7. Bank / NBFC API
Redis cache MySQL / PostgreSQL Reconciliation Worker CloudWatch

My Ownership

End-to-end ownership of banking & NBFC integrations — architecture, delivery, and the bank infrastructure clearances required to go live: vulnerability reports, application security reviews, and source code audits for banking partners. Led RD integrations for two banks and delivered three NBFC integrations from scratch, plus a serverless KYC funnel analytics pipeline (Lambda, Glue, Athena, S3) giving product teams visibility into onboarding drop-off.

Key Technical Decisions

NestJS's module boundaries kept each partner integration testable and swappable without touching the others. Slow or unreliable partner calls were pushed onto SQS/Lambda instead of the request path, so booking a product never blocks on a bank's response time. Manual reconciliation — matching what the bank confirms against what the platform recorded — was automated with Lambda instead of a human running spreadsheets at end of day.

Challenges

Each new NBFC integration (Bajaj, Mahindra, Shriram) arrived with its own payload format and edge cases that only showed up in production — inconsistent field mapping, partial failures, and timing differences between "the bank says it's booked" and "our system knows it's booked." Debugging across a 10+ service surface under a live banking partner made fast, structured triage non-negotiable.

Impact

  • API response time cut by up to 90%
  • Log volume cut by ~50%, improving observability and infra cost
  • Manual reconciliation reduced by 95%
  • RD integrations live with 2 banks; NBFC integrations live with 3 NBFCs
  • Average production issue resolution time cut from 24h to 6h
Node.js NestJS TypeScript MySQL / PostgreSQL Redis AWS Lambda SQS EventBridge CloudWatch
Case Study 02

Payment & Transaction Processing

Fixerra — collection, disbursement & refund flows across banking products

Problem

Every FD, RD, and savings product needs money to move reliably in both directions — collecting from the user (including TPV and autopay) and disbursing or refunding back — across three payment gateways and multiple bank rails. A payment status update can arrive late, out of order, or more than once; the system has to stay correct regardless.

Architecture

Gateway integrations for Razorpay, PayU, and Cashfree sit behind a common payment layer, with issuer/bank wrappers handling TPV and autopay. Gateway webhooks and bank callbacks are processed asynchronously off a queue rather than inline with the request, so a delayed or retried notification never blocks the user-facing flow — and a background reconciliation pass checks the platform's record of a transaction against what the gateway and bank actually settled.

  1. Client Request
  2. Payment Gateway (Razorpay / PayU / Cashfree)
  3. Webhook / Bank Callback
  4. Queue
  5. Status Processor
  6. Database (system of record)
Idempotency Store Retry / DLQ Reconciliation Worker Bank Settlement Report

My Ownership

Integrated all three payment gateways for collection, disbursement, and refund flows across multiple banking products, and built the Lambda-based reconciliation automation that replaced manual, end-of-day matching.

Key Technical Decisions

Payment state changes are processed as events, not as a value simply overwritten in place — so a webhook that arrives twice (a real occurrence with every gateway) can't double-credit or double-refund a user. Status updates are handled off a queue with retries, rather than assuming a callback always arrives, always arrives once, or always arrives in order. Reconciliation runs as a separate scheduled job against gateway/bank settlement data instead of trusting the callback stream alone — it's the source of truth for "did the money actually move."

Challenges

Gateways and bank rails don't fail cleanly — a request can time out on the platform's side while still succeeding on the bank's side, which looks identical to a real failure until reconciliation catches it. Getting from "spreadsheet reconciliation, once a day" to automated made the failure modes (duplicate webhooks, out-of-order callbacks, partial timeouts) impossible to ignore, since automation has to handle every edge case a human previously used judgement on. Case Study 03

AI-Assisted Production & Partner Support

Fixerra — production triage and partner query resolution across 10+ services

Problem

Owning 10+ live microservices under active banking partners means a constant stream of production issues and partner queries — malformed payloads, integration edge cases, log noise — most of which follow patterns an engineer has already seen before, but still cost real triage time to resolve.

Architecture

AI tooling (Claude, Cursor, Codex) is wired into the support workflow itself, not used ad hoc: it reads structured logs and API payloads to do first-pass analysis, drafts root-cause hypotheses, and generates test cases to confirm a fix — with a human still reviewing anything that touches production data or money movement before it ships. The team is now extending this into agents that handle first-pass triage on production issues and partner queries directly.

  1. Production Alert / Partner Query
  2. AI Triage Agent (Claude / Cursor / Codex)
  3. RCA, Suggested Fix or Draft Response
  4. Human Review (money-impacting actions)
  5. Resolution Logged
Structured Logging CloudWatch Log Aggregation

My Ownership

Introduced and drove adoption of AI-assisted workflows for API payload analysis, root-cause analysis, log triage, and test-case generation as Tech Lead, and am now leading the build-out of agents that resolve production issues and partner queries with less manual intervention.

Key Technical Decisions

AI tooling was scoped to analysis, drafting, and triage — the reasoning and legwork — rather than given standing write access to production or money-moving systems, keeping a human explicitly in the loop for anything financial. It was applied to the highest-volume, most repetitive support work first (log triage, payload analysis) where pattern-matching saves the most engineer time.

Challenges

Getting useful output requires feeding the tooling enough real context (logs, payloads, past incidents) without exposing sensitive banking data, and building enough trust in its first-pass RCA that engineers actually use it instead of re-deriving everything from scratch.
